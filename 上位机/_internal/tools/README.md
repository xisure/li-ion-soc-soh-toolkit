单节 18650（NCR18650GA / 18650-3350D，标称 3350 mAh）。
MCU 板（CH32X035 + INA226 + NTC + SSD1306）按 5 Hz 从串口吐数据，

离线验证 SOH 在线学习器。

## 1. 环境与接线

### 1.1 PC 环境

Python 3.9+，装依赖：

```bash
python -m pip install -r requirements.txt
```

> ⚠ 用哪个解释器装的依赖，就用哪个跑脚本。换了解释器（比如 IDE 自带的托管
> 环境）会直接 `ImportError`。

同时开两个终端：**终端 A** 跑控载，**终端 B** 跑采集（后文按此称呼）。

### 1.2 硬件接线

```
  放电（电子负载）                    充电（可编程电源）
   电池 + ──┬──► 负载 CH1 (+)          电源 CH1 (+) ──┬──► 电池 +
            │                                         │
            └──► MCU 采集板                            └──► MCU 采集板
   电池 − ──┴──► 负载 CH1 (−)          电源 CH1 (−) ──┴──► 电池 −
```

要点：**充/放电流必须流经 INA226 的分流电阻**，否则电流方向/大小全是错的。
两条 USB 线都插上：一条是 MCU 的调试/数据串口，一条是源/载的 RS232 口。

> 充电方向注意**共地**：可编程电源的输出地与 MCU 板地要连在一起（都接电池负端），
> 否则 INA226 读到的端压会叠加地电位差。同时给电池串口加 TVS 时别忘了电源侧。

### 1.3 串口

**不用记 COM 号**：

- `soc_record.py` 不传 `--port` 会列出系统串口让你选（只有一个串口时直接采用）。
- `soc_load.py` 不传 `--port` 会自动探测源/载（见 [3.2](#32-soc_loadpy--源载控载放电--充电)），
  认不出来才退回串口菜单/手输。
- 波特率：MCU 数据口默认 115200；源/载口固定 9600（脚本内部写死，不用管）。

## 2. 串口协议

MCU → PC，文本行，CRLF 结尾，5 Hz（每 200 ms 一帧）：

```
D,V_mV,I_mA,T_0p1C,SOC_0p01,SOH_0p01,Q_mAh,R0_mohm
```

| # | 列 | 单位 | 说明 |
| --- | --- | --- | --- |
| 0 | `D` | — | 数据帧前缀（Data）。**无前缀的行一律丢弃**，用于和上电诊断打印区分 |
| 1 | `V_mV` | mV | 电池电压，整数 |
| 2 | `I_mA` | mA | 总线电流，**放电为正 / 充电为负** |
| 3 | `T_0p1C` | 0.1 °C | `253` = 25.3 °C |
| 4 | `SOC_0p01` | 0.01 % | MCU 当前 SOC（`10000` = 100.00 %） |
| 5 | `SOH_0p01` | 0.01 % | MCU 在线学习的 SOH（容量 Q / 内阻 R0 取劣） |
| 6 | `Q_mAh` | mAh | 在线学到的可用容量（回写 `soc.c`，SOC 立刻按新值换算） |
| 7 | `R0_mohm` | mΩ | 学习后的 10~90 % 平均欧姆内阻 |

示例：

```
D,3845,1234,253,8654,9666,3238,62     放电 1.234 A, 3.845 V, 25.3 °C, SOC 86.54 %, SOH 96.66 %
D,4102,-1500,246,9120,9666,3238,62    充电 1.500 A（电流为负）
D,0,0,253,0,0,0,0                     占位帧（INA226 掉线）——V=0 会被采集端丢弃
```

**向后兼容**：字段较少的旧固件帧（`D,V,I,T` / `D,V,I,T,SOC`）同样能解析，
缺失的列在 CSV 里留空，历史 CSV 无需重录。

## 3. 脚本详解

### 3.1 `soc_record.py` — 串口采集

**职责**：只做"收数据 + 落盘"，**不参与任何 SOC 计算**。由 PC 端打时间戳。

```bash
python soc_record.py --out stair1.csv          # 交互选 COM 口 + 波特率
python soc_record.py --port COM3 --baud 115200 --out stair1.csv   # 全参数，免交互
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--port` | 交互选择 | 串口号 |
| `--baud` | 交互选择 | 常用 115200 |
| `--out` | 终端提示 | 输出 CSV 路径 |

- **Ctrl+C** 停止并保存（已写入的行不会丢）。
- 输出 CSV 表头：
  `time_iso, elapsed_s, V_mV, I_mA, T_0p1C, SOC_0p01, SOH_0p01, Q_mAh, R0_mohm`
  （`time_iso` = PC 端 ISO 时间戳，`elapsed_s` = 距首帧秒数）
- 内置量程护栏（只挡串口垃圾，不做精度判断）：
  V 1500~5000 mV、I ±30 A、T −40~+125 °C，超范围整行丢弃。

### 3.2 `soc_load.py` — 源/载控载（放电 + 充电）

**职责**：通过 RS232（9600，SCPI）控制**程控电子负载**（放电）或
**可编程电源**（充电），自动跑 N 档（默认 10）"**恒流充/放 → 断开静置**"周期，
供 MCU 侧同步采集做 R0/R1/OCV/SOC 标定。

**方向用 `--charge` 切**：不加就是放电。两个方向的差异全部收在顶部一张 `MODES`
表里（开关命令、保护方向、默认区间、默认电流、产物名），控制流程只有一条：

| | 放电（默认） | 充电（`--charge`） |
| --- | --- | --- |
| 设备 | 程控电子负载 | 可编程电源 |
| 开关命令 | `INP 1` / `INP 0` | `OUTP 1` / `OUTP 0`（另发 `VOLT {v}` 定 CV） |
| **脚本**中止门限 | `--vlimit` = 端压**底线**，默认 2.8 V | `--vlimit` = 端压**上限**，默认 4.15 V |
| **设备**自我保护 | —（负载本身不设限） | `--vset` 电源 CV 设定，默认 4.20 V |
| 默认区间 | 100 % → 9 % | 9 % → 80 % |
| 默认电流 | 2.0 A | 1.6 A（≈0.5C） |
| 产物前缀 | `load_segments` | `charge_segments` |
| 端压关系 | 端压 = OCV − I·R | 端压 = OCV + I·R |

**不交互也能选方向**：直接跑 `python soc_load.py` 时，终端里会问一句
"方向 1=放电 / 2=充电"（回车=放电）；非交互（`--yes` 或 stdin 不是终端）时
不会问，只认 `--charge`。

**这个脚本不绑定设备型号**：用的是通用 SCPI 根命令方言（`CURR` / `INP` / `OUTP` /
`VOLT` / `MEASure:VOLTage?` / `MEASure:CURRent?`），艾德克斯 IT8500 / IT6300 同族
以及多数国产源载都是这套；换品牌若写法不同，用 `--cmd` 覆盖那几条即可，
控制逻辑一行都不用改（详见下面的"通用性"）。

```bash
python soc_load.py                                   # 全交互（会问方向），缺省回车
python soc_load.py --port COM7 --capacity 3350 --current 2.0 \
                --to-soc 9 --rest-s 480 --cutoff 2.8
python soc_load.py --charge --port COM8 --current 1.6 \
                --to-soc 80 --vlimit 4.15 --vset 4.20    # 充电标定
python soc_load.py --demo --segments 3 --pulse-s 1 --rest-s 1   # 空载快速联调
```

> **充电默认只跑到 80 %**：再往上端压（OCV + I·R）会顶到电源的 CV 设定值，
> 一进 CV 电流就自己衰减，每档时长不再受控、拟合会被带偏。
> 想标高端就把电流调小（比如 0.5 A），或者改用"CV 段电流衰减到 C/20"那一段。

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--charge` | 关 | 切到充电方向（控可编程电源 + 端压上限保护） |
| `--port` | 自动探测 | 不传则自动找设备口（见下），认不出来再列串口菜单 |
| `--peer-port` | 空 | **跨设备互锁**：另一台设备的串口。给了它，开跑前会先连上那台、按反方向下发断开命令并复核电流，确认断开才驱动本腿设备 |
| `--peer-off` | 按反方向自动 | 覆盖给伙伴设备下发的断开命令（放电腿默认给电源 `OUTP 0`，充电腿默认给负载 `INP 0`） |
| `--idn` | 空 | 自动探测时按 IDN 关键字收窄（逗号分隔），如 `--idn ITECH`；缺省=谁应答 `*IDN?` 就认谁 |
| `--cmd` | 空 | 覆盖命令方言表，可重复，如 `--cmd "on=LOAD:STATe 1"`（换品牌用）；充电方向另有 `vset` / `volt_q` 两个键 |
| `--capacity` | 3350 | 电池容量 mAh |
| `--init-soc` / `--to-soc` | 放电 100 / 9；充电 9 / 80 | 覆盖区间（放电末点 9 % 覆盖低端非线性段；充电末点 80 % 避开 CV） |
| `--spacing` | `ocv` | `ocv` = 每档**压降**相等（陡段自动加密）；`soc` = 每档 SOC 相等 |
| `--segments` | 10 | 档位数 |
| `--current` | 放电 2.0；充电 1.6 | 每档电流 A，可写 `0.5:3` 递变或逗号序列 |
| `--rest-s` | 480 | 档间静置秒数 |
| `--vlimit`（别名 `--cutoff`） | 放电 2.8；充电 4.15 | **脚本自己的中止门限**：放电＝端压底线，充电＝端压上限。方向不对会当场报错 |
| `--vset` | 4.20 | **[仅充电]** 电源 CV 设定值（V）。**必须高于 `--vlimit`**，让脚本先收手 |
| `--ocv-table` | 内置表 | 覆盖 OCV 表（11 个 mV），影响断点校验与末档估算 |
| `--out` | 放电 `load_segments`；充电 `charge_segments` | 输出文件名前缀 |
| `--demo` / `--pulse-s` | — | 空载联调：跳过试拉与门限检查，固定脉冲时长 |

**为什么 `--spacing ocv` 是默认**：OCV-SOC 曲线中段线性（每档放得多），两端
尤其低 SOC 段斜率大（每档自动加密），这样喂给 MCU 线性查表时每档的电压分辨率
才一致。档位断点由固件 OCV 表反解，所以**改过 OCV 表要一起改**。

**六道安全保护**（两个方向全程生效，只是门限方向相反）：

1. **端压门限**：加载中每 3 s 轮询端压，**越过** `--vlimit` 立即断开
   （放电是"低于"，充电是"高于"）；
2. **断点校验**：每档开始时实测开路电压须在内置 OCV 表预期 ±0.5 V 内，
   否则中止（常见于：电池没充满 / 容量或表与电芯不符 / 接错电池组）；
3. **带载确认**：开载后 1.5 s 实测电流的**绝对值**须达设定值的 85 % 以上，
   否则视为线断或接触不良，断开中止（取绝对值是因为负载/电源/MCU 三套电流
   符号约定互不相同，判据不能依赖符号）；
4. **通信看门狗**：加载中连续 3 次读不到设备 → 强制断开并终止；
5. **异常兜底**：Ctrl+C / 任何异常走 `finally` 必发断开命令；若断开指令本身
   失败会明确警告你去面板手动断；
6. **跨设备互锁**（`--peer-port`，两台并接时才需要）：开自己的串口**之前**，
   先连上另一台、下发它的断开命令并复核实测电流 ≈ 0；确认不了就中止，
   绝不"先开自己再说"。

> 充电方向另外自查一条：**`--vlimit` 必须低于 `--vset`**。前者是脚本的中止判据，
> 后者是电源自己的 CV 设定；写反了就等于没有脚本级保护，全靠电源硬件兜。
> 默认 4.15 / 4.20 就是这个关系。

#### 两台设备并接同一节电池：`--peer-port` 互锁

做多轮充放循环（或任何"这台跑完换那台"的测试）时，电子负载和可编程电源会**同时并接
在同一节电池上**，同一时刻只允许有一台导通。脚本只管得着自己那台（`finally` 里断开），
另一台的开关状态是上一腿或人留下的 —— 上一腿异常退出（拔线 / 掉电 / 被强杀）就可能把
它留在导通态，这一腿一开输出，两台就对打。

给一个 `--peer-port` 就把这段补上：

```bash
python soc_load.py          --port COM9 --peer-port COM8     # 放电腿：先关电源 COM8
python soc_load.py --charge --port COM8 --peer-port COM9     # 充电腿：先关负载 COM9
```

开跑前的顺序是**固定**的，不可颠倒：

```
① 连伙伴 → ② 下发它的断开命令(重试3次) → ③ 复核实测电流≈0 → ④ 关伙伴串口 → ⑤ 才开自己
```

三条要留意的：

- **伙伴是谁、发什么命令是自动推出来的**：本腿放电 ⇒ 伙伴是电源 ⇒ `OUTP 0`；本腿充电
  ⇒ 伙伴是负载 ⇒ `INP 0`。只有换品牌命令不同时才需要 `--peer-off` 覆盖。
- **确认不了就中止**（fail-closed）：伙伴连不上、不应答 `*IDN?`、断开命令发不出去、
  或断开后实测电流仍有 ≥ 50 mA —— 都会直接停下，**本腿设备的串口压根不会被打开**。
- **唯一"不算失败"的情况**：伙伴不支持读电流（`MEASure:CURRent?` 无响应或回非数值）。
  那时日志会写"只确认到命令已下发，请目视面板" —— **别把它当成复核过了**。

> ⚠ 互锁是**命令级**的，不是电气级的。两个前提得自己保证：两台设备的"断开"确实是
> 高阻（首跑时用串联电流表或电流探头确认一次），以及电源没开"上电自动输出 /
> Auto-Recover"。这两条不成立的话，软件再严也拦不住。

#### 档位计划文件（"自动识别档位"的钥匙）

跑完一次，在 `--out` 前缀旁落两份东西：

| 文件 | 给谁看 |
| --- | --- |
| `<前缀>.csv` | **人看**的档位明细（每档起止时刻、设置电流、实测端压） |
| `<前缀>.json` | **机器读**的计划：`format: "soc-plan/1"`，含容量、起末 SOC、每档断点、设置电流、计划 mAh、OCV 表、跑了多少档、有没有中途中止 |

**把它改名成 `<record.csv 前缀>_plan.json` 放进同一目录**，`stair` 就会自动认
（见 [3.3④](#-stair--多档周期分析主力)），届时 `--capacity` / `--init-soc` /
`--expect` 一个都不用输。改名之前扫一眼 `aborted` 字段：中途被保护中止的计划
只能给"打算跑什么"，容量与起末 SOC 仍然是对的，但档数要按实际算。

#### 通用性：怎么自动找设备口 / 怎么换品牌

**自动探测**（不传 `--port`）：逐个串口做两步，都与品牌无关，每个口约 0.6 s。

1. **静默检查**：先只听 0.3 s。**主动往上报数据的口不是源/载** —— 它们只在被问的
   时候才说话，MCU 数据口是 5 Hz 不停吐的。少了这一步，MCU 口吐的 `D,...` 帧会被
   当成 `*IDN?` 的应答，认成源/载。
2. **应答 `*IDN?`**：谁应答谁就是候选，同时把 IDN 原样打出来。是不是真设备由后面
   的"试拉 0.1 A"兜底确认。

不按品牌筛是有意的：命令集本身就是通用写法，认品牌只会把没见过的牌子挡在外面。
想收窄就加 `--idn ITECH`。蓝牙 SPP / Intel AMT-SOL 这类假串口按描述直接跳过
（它们的 `write` 会等超时，每口白等一秒）。

**命令是"数据"不是"代码"**：命令放在 `soc_load.py` 顶部的 `CMDS` 表里
（公共 6 条 + 充电方向另加 `vset` / `volt_q`），换品牌只改表，控制流程一行不动；
也可以不改代码，用命令行覆盖：

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `curr` | `CURR {i}` | 设 CC 电流，`{i}` 会被替换成数值（A） |
| `curr_q` | `CURR?` | 读回设定电流（只用于日志校验，不支持时返回空即可） |
| `on` / `off` | 放电 `INP 1` / `INP 0`；充电 `OUTP 1` / `OUTP 0` | 加载 / 卸载 |
| `volt` / `amp` | `MEASure:VOLTage?` / `MEASure:CURRent?` | 读端压 / 读电流 |
| `vset` / `volt_q` | `VOLT {v}` / `VOLT?` | **[仅充电]** 设 / 读电源 CV 值 |

```bash
# 例：开关命令走 LOAD:STATe 的品牌
python soc_load.py --cmd "on=LOAD:STATe 1" --cmd "off=LOAD:STATe 0"
```

键名或写法不对会**直接报错退出**（不静默忽略）。方言填错也不会把电池放空：
读不到电压要么被通信看门狗抓到，要么端压读到 0 V 直接触发截止保护断开。

> 附：默认方言为什么是这套 —— SCPI 允许省略可选的根节点，所以 `CURR 2` 与
> `:SOURce:CURRent 2` 等价、`INP 1` 与 `:INPut:STATe 1` 等价。手册上写成哪个都
> 不影响，只要电压电流是 `MEASure` 节点、开载是 `INPut` 节点（这是 SCPI 里最统一
> 的部分）。真正各家不同的是开关命令的节点名，所以那两条留了覆盖口子。

### 3.3 `soc_bench.py` — 主工具

**职责**：统一入口 + 四类动作（采集 / 单脉冲拟合 / 多档分析 / 多轮循环）。不带子命令时是**交互向导**。

```bash
python soc_bench.py                                # ① 向导：先选程控/手动
python soc_bench.py record --out pulse1.csv        # ② 采集（等同 soc_record.py）
python soc_bench.py fit --csv pulse1.csv           # ③ 单脉冲 RC 拟合
python soc_bench.py stair --csv stair1.csv         # ④ 多档分析（参数自动从计划文件取）
python soc_bench.py cycle --cycles 5               # ⑤ 多轮充放循环（老化/一致性）
```

#### ① 向导（无子命令）

问"程控 / 手动"：选程控就直接拉起同目录 `soc_load.py` 走完整流程
（**方向由它接着问你**：1=放电 / 2=充电）；选手动则只做采集。日常用向导即可。

#### ② `record` — 采集

参数与 `soc_record.py` 完全一致（协议常量共用），只是入口统一到 `soc_bench.py` 下。

#### ③ `fit` — 单脉冲 RC 拟合

从"恒流放电 60~120 s → 断开静置 ≥10 min"的一段数据里自动找断电点，拟合：

```
R0  = 断电瞬间电压跳变 / 放电电流
R1  = 静置段指数回弹幅度 / 放电电流
tau = 指数恢复的 ln 线性回归斜率
C1  = tau / R1
模型: V(t) = OCV − I·R0 − V_rc
      静置恢复 V(t) = V_inf − I·R1·exp(−(t−t_off)/tau)
```

| 参数 | 说明 |
| --- | --- |
| `--csv` | 要分析的 CSV；缺省则扫描当前目录交互选择 |
| `--I` | 已知放电电流（A），指定则用它替代均值，**防误判** |

#### ④ `stair` — 多档周期分析（主力）

自动把整段录制切成 N 个"充/放-静置"档，逐档拟合 `R0/R1/C1/tau`，
取各档前后 OCV，用安时积分定 SOC → 汇总成 **OCV-SOC 表 + R(SOC) 表**。

**充放电通吃**：`find_pulses` 判 `|I|`、`r0 = dv/i`（分子分母同号，结果恒正）、
安时积分符号自动、OCV 取静置尾均值 —— 这些本来就与方向无关。为了让**充电数据**
也能跑，另外通了三处判据：静置回弹的 `fit_relax`（放电后电压**升**、充电后**降**，
现按符号归一）、`fit` 里"只接受放电数据"的拦截、OCV 表单调性（**按 SOC 排序后判**，
按时间序在充电数据上必然误报）。

**参数不用手工输**：`--capacity` / `--init-soc` / `--expect` 都可省，
按 **命令行 > 档位计划文件 > 标称值/电压反查** 三级自动确定，屏幕上会写清每级用了什么。

**档位计划自动识别**（`soc_load.py` 跑完落的 `<前缀>_plan.json`，见 [3.2](#32-soc_loadpy--源载控载放电--充电)），
按优先级找：

1. `--plan 路径` 显式指定；
2. 与 `--csv` **同前缀**的 `_plan.json` / `_segments.json` / `_load_segments.csv` /
   `_charge_segments.csv` / `_segments.csv`；
3. 同目录里**唯一**的一份 `*_plan.json`（兜底。命中时会**明确打印**用的是哪份并
   提醒你显式指定 —— 前缀对不上就是给"忘了改名"救急用的，不会闷声拿错）。

```bash
python soc_bench.py stair --csv stair1.csv                    # 自动找 stair1_plan.json
python soc_bench.py stair --csv stair1.csv --plan seg.json    # 显式指定
```

**计划 vs 实测逐档对拍**：认到计划后拿它的断点 / 电流 / 容量去比实测，逐档打
"吻合 / 不符"，并单独检查**计划方向与实测方向是否一致**（充电数据配了放电计划
会直接点出来）。电流一律比**幅值** —— 计划里存的是设置值，实测的是带符号值，
两者符号约定未必同源。

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--csv` | 交互选择 | 要分析的 CSV |
| `--plan` | 自动找 | 档位计划文件（见上）；填 `none` 关掉不认，容量/起始 SOC 自己给 |
| `--capacity` | 计划 > 3350 | 标称容量 mAh（与固件 `SOC_CAPACITY_NOMINAL_MAH` 一致） |
| `--init-soc` | 计划 > 电压反查 | 起始 SOC %。**不能默认 100** —— 充电时 SOC 是往上走的，猜错整条曲线平移 |
| `--ocv-table` | 内置表 | 反查起始 SOC 用的 OCV 表（11 个 mV） |
| `--i-on` / `--i-off` | 200 / 50 | 带载进入/退出阈值 mA（滞回，防边缘抖动） |
| `--idle-ma` | 20 | 静置判定阈值 mA（与固件 `soc.c` 一致） |
| `--min-pulse-s` | 2.0 | 短于此的带载段当毛刺丢弃 |
| `--ocv-tail` | 60 | OCV / V_inf 取静置段**末尾**多少秒的均值 |
| `--expect` | 计划 > 10 | 期望档位数，不符只提示不报错 |
| `--out` | 与 CSV 同名 | 输出文件前缀 |
| `--zero-drift` | 关 | 扣除静置段电流零漂后再积分（默认不扣，**保持与 MCU 侧一致**） |
| `--emit-c` | 关 | 额外打印固件用的 11 点 OCV 查表 C 数组 |
| `--no-plot` | 关 | 只出表不出图 |

产物：`<前缀>_stair.csv`（档明细，即 `--refs` 的输入）、
`*_stair_ocv.csv`、`*_stair.json`、`*_stair.png`、`*_stair_timeline.png`。
（图形界面里跑的话，后两张图跑完会**直接显示在④页上半个面板**，不用去文件夹找 —— 见 §7.3）

#### ⑤ `cycle` — 多轮充放循环（老化 / 一致性）

把"放电腿 → 充电腿"自动交替跑 N 轮，用来做循环老化、一致性对比。
**每一腿都是一次完整的 `soc_load.py` 运行**，所以每腿各自落一份计划 + 档位时刻表，
哪一腿出问题只丢那一腿，已经跑完的腿不受影响，也不用为了接着跑而重头再来。

```bash
python soc_bench.py cycle --cycles 5 --dry-run                    # 先看腿序/预计总时长，不碰设备
python soc_bench.py cycle --cycles 5 --port-load COM9 --port-psu COM8
```

排出来的腿序**首尾相接**（后一腿从前一腿的终点起步）：

```
放电 100%->9% | 充电 9%->80% | 放电 80%->9% | 充电 9%->80% | ...
  └ 第一腿宽一点        └ 从第二腿起每一轮都是 9%<->80%：窗口一样，轮与轮才谈得上可比
    （电池刚充满）
```

产物前缀 `cyc_c1_dis` / `cyc_c1_chg` / `cyc_c2_dis` …（`--prefix` 可改），
即每腿一份 `cyc_c1_dis.json`（计划）+ `cyc_c1_dis.csv`（档位时刻表）。

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--cycles` | 3 | 循环轮数（每轮 2 腿） |
| `--first` | `discharge` | 第一腿方向 |
| `--soc-hi` / `--soc-lo` | 80 / 9 | 循环窗口两端 % |
| `--start-soc` | 100（放电首） | 第一腿起始 SOC %。电池刚充满就用默认，它会先把这一段放到窗口下沿 |
| `--segments` | 10 | 每腿档位数 |
| `--current-load` / `--current-charge` | 2.0 / 1.6 | 两腿每档电流 A |
| `--rest-s` | 480 | 档间静置 s |
| `--vlimit-load` / `--vlimit-charge` | 2.8 / 4.15 | 两腿的脚本中止门限 V |
| `--vset` | 4.20 | 电源 CV 上限（**必须高于** `--vlimit-charge`，先撞 CV 就等于没保护） |
| `--port-load` / `--port-psu` | — | 两台设备的串口。**必须给全** —— 互锁全靠它知道"另一台在哪"，也是真跑的前置条件 |
| `--cmd-load` / `--cmd-chg` | 空 | 两条腿**各自**的命令方言覆盖（可重复，换品牌用）。电子负载和可编程电源可能是两个牌子，所以分开传；每条方言只作用于那一腿自己的设备 |
| `--no-interlock` | 关 | 不要求给全两个口，也不做跨设备互锁（缺口时唯一的放行方式） |
| `--capacity` | 3350 | 标称容量 mAh |
| `--prefix` | `cyc` | 产物前缀 |
| `--keep-going` | 关 | 某腿没跑满也接着跑后面的腿（默认停下） |
| `--dry-run` | 关 | 只打印腿序 / 预计时长 / 命令行 |
| `--yes` | 关 | 不再确认，直接开始 |

**某腿没跑满就默认停下**：后面每腿的起始 SOC 是按"上一腿跑满"推出来的，硬接着跑会
从一开始就对不上（`soc_load.py` 的断点 OCV 校验也会先把它拦下来）。确认电池实际 SOC 与
该腿起点一致后，再加 `--keep-going` 跑完剩下的腿。

**账要先算清楚再开跑**：一条 100 %→9 % 的放电腿 ≈ 2.9 h、9 %→80 % 的充电腿 ≈ 2.8 h，
5 轮 ≈ 28 h。这个预计值是用 `soc_load.py` 自己的 `build_breaks` / `currents_for` 算的
（不是另写一份近似），所以和真跑对得上；`--dry-run` 会把它逐腿列出来。

**互锁是强制的**：`cycle` 每一腿都会带上 `--peer-port`（充电腿关负载、放电腿关电源），
所以**两个口都得给全**，否则真跑会被直接拦下来：

```
[X] 多轮循环是两台设备并接交替跑, 要显式给全两台的口才能互锁:
     --port-load COM9 --port-psu COM8
    缺一个口时, 那一腿的自动探测会在两台同插时挑错, 互锁无从建立。
    确实不用互锁(或只跑 --dry-run)就加 --no-interlock 明确放行。
```

道理是：缺一个口时那一腿只能靠自动探测找自己的设备，而**两台都在线时两台都会应答
`*IDN?`** —— 探测会挑错，互锁就无从建立。互锁的原理与边界见
[3.2 的"两台设备并接"](#两台设备并接同一节电池--peer-port-互锁)。

`--dry-run` 是例外：它只打印、不碰设备，所以缺口时也照列命令行（只会提示一句），
方便先看腿序与预计时长。

> ⚠ 循环测试一般让 `soc_record.py` **全程连续录一整段**，跑完再按每腿 json 里的
> `t_start` / `t_rest_end` 把采集切段。**目前还没有自动切段工具**，需要手工切
> 或者每腿单独起停一次采集。

> ℹ `cycle` 的窗口两端（80 / 9）刻意与 `soc_load.py` 的方向默认值对齐 —— 这就是
> "两腿首尾相接"能成立的原因。改任何一边都要两边一起改，`test/check_consts.py`
> 的第 [9] 段会替你把这条守住。

### 3.4 `test/kalman_tune.py` — EKF 调参

**职责**：一阶 RC EKF 的离线参数迭代 + MCU 移植一致性校验。模型与固件 `soc.c`
**逐行对齐**（改模型必须两边同步）。

```
x = [soc(%), vrc(mV)]
soc'  = soc − I·dt/(cap_mah·3600)·100          放电为正
vrc'  = a·vrc + I·R1(soc)/1000·(1−a),   a = exp(−dt/tau(soc))
z = V_m,  h = OCV(soc) − I·R0(soc)/1000 − vrc,  H = [dOCV/dsoc, −1]
Q = diag(q_soc, q_vrc)（每帧）,  量测噪声 R（mV²）,  野值 |res| > 250 mV 丢弃
```

```bash
# 网格调参：以 stair 静置末参考点打分，选最优 (q_soc, q_vrc, R)
python test/kalman_tune.py --csv stair1.csv --refs stair1_stair.csv

# 只跑一组：与固件同参回放，和 CSV 里 MCU 实跑的 SOC 轨迹逐帧对比
python test/kalman_tune.py --csv stair1.csv --refs stair1_stair.csv --param 0.001 0.5 10

# 用自己的参数跑一遍并出轨迹图（不用烧板就能看改参数的效果）
python test/kalman_tune.py --csv stair1.csv --param 0.002 1.0 8 --plot my.png

# 快速看：只取前 N 帧
python test/kalman_tune.py --csv stair1.csv --param 0.01 1.0 5 --limit 30000

# 固件里现在跑的到底是哪一组（从 bms_config.h 现读，不是另抄的）
python test/kalman_tune.py --print-fw-default
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--csv` | 必填 | `soc_record.py` 采集的 CSV |
| `--refs` | — | `*_stair.csv`，提供静置末安时参考点（**打分主基准**） |
| `--param` | — | 只回放这一组 `q_soc q_vrc R` —— **想用自己的参数跑仿真就填这个** |
| `--grid` | 4×3×3 | 三组档位列表，组间用 `\|` 分隔（如 `1e-3,1e-2 \| 0.5 \| 5,20`），各档逗号分隔 |
| `--plot` | — | 把轨迹画成 PNG：① SOC 轨迹（PC 回放 / MCU 实跑 / stair 静置末参考点）② 误差 ③ 电流与电压。配 `--param` 画单组，网格模式画最优那组。**图形界面里勾「跑完出轨迹图」即可，跑完图直接显示在⑥页上半个面板**（见 §7.3） |
| `--limit` | — | 只取前 N 帧 |
| `--print-fw-default` | — | 打印从 `../算法库/bms_config.h` 现读的 EKF 三参数后退出 |

**用自己造的工况跑**：`--csv` 只认 `elapsed_s,V_mV,I_mA` 三列（第四列 `SOC_0p01`
是 MCU 回传的 SOC，没有也能跑，只是少了 MCU 对比）。所以拿 Excel 拼一段自己的
电流/电压序列，存成 UTF-8 CSV 就能喂进来 —— 不必非得是这台板子采的。

**评估基准优先级**：`refs`（stair 静置末参考）> `mcu`（MCU 回传轨迹）> `idle`（端压自洽）。

### 3.5 `soh_learn.py` — SOH 离线验证

**职责**：把 SOH 学习算法搬进 MCU **之前**，先用实测数据回放验证精度。
这是**离线分析视角**（numpy 向量化、事后扫静置段），可以用未来数据。

```bash
python soh_learn.py --csv stair1.csv --refs stair1_stair.csv
python soh_learn.py --csv stair1.csv --scale 0.80     # 合成老化：真容量缩到 80 %
python soh_learn.py --csv stair1.csv --emit-c         # 输出学习后的 C 数组
python soh_learn.py --csv stair1.csv --plot           # 出图（R0 vs SOC）
```

**判据**（与 `soc_bench.py` 的 `find_pulses/analyze_seg` 一致）：

```
R0 = (断电后第一静置帧电压 − 带载末 5 帧均值电压) / 带载电流均值
Q  = 两个 OCV 锚点之间的库仑计数 / OCV 查表得到的 ΔSOC
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--csv` | 必填 | 采集的 CSV |
| `--refs` | — | `stair1_stair.csv`，用于对比 PC 端拟合的 `r0_mohm` |
| `--scale` | 1.0 | 合成老化：真实容量 = scale × 3350 |
| `--i-on` / `--i-off` | 500 / 200 | 带载滞回门限 mA |
| `--min-pulse` | 5.0 | 最短带载时长 s |
| `--min-dsoc` | 15.0 | 触发容量学习的最小 ΔSOC % |
| `--alpha-r0` | — | R0 遗忘因子（默认同固件） |
| `--emit-c` / `--plot` | — | 输出 C 数组 / 出图 |

### 3.6 `soh_mcu_sim.py` — MCU 逐帧复刻

**职责**：把固件 SOH 状态机的逻辑**逐行搬到 PC**，用同一份 CSV 回放，验证移植无误。
这是 **MCU 运行视角**：逐帧状态机、同样的整数-浮点混合、同样的自适应 α、
同样的限幅顺序 —— **只用当前帧及历史帧，不碰未来数据**。

```bash
python soh_mcu_sim.py --csv stair1.csv --refs stair1_stair.csv
python soh_mcu_sim.py --csv stair1.csv --scale 0.8
```

| 参数 | 说明 |
| --- | --- |
| `--csv` | 采集的 CSV |
| `--scale` | 合成老化：真容量 = scale × 3350（与 `soh_learn.py` 同口径） |
| `--refs` | `stair1_stair.csv`，对比 R0 |

**启动时会做常量体检**：把脚本侧的判据常量与 `soh_learn.py` 的逐项比对，
不一致就报警 —— 防止两边改了一边。所以 `soh_mcu_sim.py` 和 `soh_learn.py` 必须同目录。

与 `soh_learn.py` 的分工：

| 脚本 | 视角 | 用途 |
| --- | --- | --- |
| `soh_learn.py` | 离线（事后全局，可用未来数据） | **定算法** |
| `soh_mcu_sim.py` | 在线（逐帧因果，只用历史） | **定移植** |

两者结果应当**逐项吻合**；不吻合就说明 MCU 实现和验证脚本脱节了。

## 4. 完整测试流程

一次完整的标定 = **准备 → 采集 → 分析 → 调参闭环 → SOH 验证**，
约 3 h（其中 2.8 h 是设备自动拉档，人可以走开）。

### 阶段 0 · 准备

1. **烧录最新固件**（串口上报含 SOC/SOH/Q/R0 全部 8 列）。
   若固件上报的字段较少，CSV 后三列会空着，`soh_*.py` / `kalman_tune.py` 的 MCU 对比也失效。
2. 电池**充满 4.20 V**，静置 **≥ 30 min**（让极化恢复，否则首档 OCV 偏高）。
3. 按 [1.2 接线](#12-硬件接线)接好，两条 USB 都插上。
4. `pip install -r requirements.txt`。

### 阶段 1 · 采集（终端 B 先开，终端 A 后开）

**终端 B**（先开，录 5 min 静置基线）：

```bash
python soc_record.py --out stair1.csv
```

选 MCU 口。看到 `D,3xxx,~0,2xx,...` 刷屏即正常。

**等 5 min**，让首档静置 OCV 有据可依，然后 **终端 A**（控载）：

```bash
python soc_bench.py
```

向导逐步输入：`1`（程控源/载）→ 方向 `1`（放电）→ `y` → 一路回车接受默认
（10 档、100 % → 9 %、ΔOCV 等分、2 A、档间静置 480 s、端压底线 2.8 V）
→ **核对计划表** → 回车开始放电。

此后约 **2.8 h** 全自动。Ctrl+C 可安全中止（会断设备）。

**跑完先给计划文件改名**（后面 `stair` 靠它自动认参数）：

```bash
# soc_load.py 落了 load_segments.csv + load_segments.json
copy load_segments.json stair1_plan.json     # 与 stair1.csv 同前缀即可
```

### 阶段 1-b · 充电方向标定（可选，要可编程电源）

想要**充电方向**的 R0/R1/τ/OCV 就把源接上，同一条流程换个方向：

```bash
python soc_load.py --charge --port COM8 --current 1.6 --to-soc 80 --vlimit 4.15
```

默认 **9 % → 80 %**、1.6 A、档间静置 480 s，产物前缀 `charge_segments`。
跑完同样改名，`stair` 就会自动认出容量与起始 SOC：

```bash
python soc_bench.py stair --csv stair2.csv      # 不用再输 --capacity/--init-soc/--expect
```

> ⚠ 充电 / 放电的 OCV 有**迟滞**，这样标出的表是"充电方向的表"，
> **不要直接拿去替换 `soc_config.h` 里的放电表**。它的正经用处有两个：
> ① 给充电工况的估算做参考；② 用"CC-CV 进 CV 后电流衰减到 C/20 时 SOC ≈ 100 %"
> 这个**天然锚点**去校准 `--init-soc`（这是唯一不用猜的锚点）。

### 阶段 1-c · 多轮充放循环（可选，老化 / 一致性）

要跑多轮而不是一轮，用 `soc_bench.py cycle` 把上面两条腿自动交替起来（它内部就是反复
调 `soc_load.py`，保护与产物完全一样）：

```bash
python soc_bench.py cycle --cycles 5 --dry-run                    # 先看腿序与预计总时长
python soc_bench.py cycle --cycles 5 --port-load COM9 --port-psu COM8
```

不想敲命令就在上位机 ③ 控载页把**模式**选成「循环」（见第 7 节），两个串口同样都要填。

第一腿默认 100 % → 9 %，之后每轮都是 9 % ↔ 80 % 首尾相接（参数见
[3.3 ⑤](#33-soc_benchpy--主工具)）。采集一般让它连续录一整段，跑完再按每腿 json 的
起止时刻切段。

> ⚠ `cycle` 每腿都会做**跨设备互锁**（跑前先关另一台），所以 `--port-load` /
> `--port-psu` **两个都得给**，缺一个时真跑会被直接拦下。原理见
> [3.2 的"两台设备并接"](#两台设备并接同一节电池--peer-port-互锁)。

### 阶段 2 · 分析

设备跑完后，**先在终端 B 按 Ctrl+C** 停采集（确保最后几档静置段落盘），然后：

```bash
python soc_bench.py stair --csv stair1.csv
# 容量 / 起始 SOC / 期望档数会自动从 stair1_plan.json 取；
# 想锁死就照旧写上 --capacity 3350 --init-soc 100 --expect 10
```

输出：10 档参数表 + OCV-SOC 表 + 与 MCU 回传 SOC 的对比块；
同时生成 `stair1_stair.csv` / `stair1_stair_ocv.csv` / `stair1_stair.png` 等。

**这一步的产物是后面所有脚本的输入**，尤其 `stair1_stair.csv`。

### 阶段 3 · EKF 调参闭环

```bash
# 3.1 网格调参，以 stair 静置末参考点打分
python test/kalman_tune.py --csv stair1.csv --refs stair1_stair.csv
```

选出最优 `(q_soc, q_vrc, R)` 后：

1. 改 `../算法库/bms_config.h` 的 EKF 参数组；
2. 重新烧录；
3. **下一轮采集**用同一组参数回放做一致性校验：

```bash
python test/kalman_tune.py --csv stair2.csv --refs stair2_stair.csv --param 0.001 0.5 10
```

`mcu_rms ≈ 0` 说明板子上的 `soc.c` 与 PC 模型完全一致，移植无误。

### 阶段 4 · SOH 验证

```bash
# 4.1 离线视角：定算法（应与 MCU 行为一致）
python soh_learn.py  --csv stair1.csv --refs stair1_stair.csv

# 4.2 MCU 视角：逐帧复刻（与 4.1 逐项对照）
python soh_mcu_sim.py --csv stair1.csv --refs stair1_stair.csv

# 4.3 合成老化：验证能不能学到衰减后的容量（否则"学到 3350"可能只是自证）
python soh_learn.py   --csv stair1.csv --scale 0.8
python soh_mcu_sim.py --csv stair1.csv --scale 0.8
```

同时核对板子回传的三列（`SOH_0p01 / Q_mAh / R0_mohm`）是否与 4.1/4.2 的结论同量级。

### 阶段 5 · 换电芯 / 重标定后

1. 重跑阶段 1~2，得到新的 OCV / R0 / R1 / τ 表；
2. `soc_bench.py stair ... --emit-c` 打印 11 点 C 数组，贴回固件标定表；
3. 同步更新 `test/kalman_tune.py`、`soh_learn.py` 顶部的同名表（见[第 5 节](#5-固件--pc-常量同步表)）；
4. **`python test/check_consts.py`** —— 上面那张同步表逐项自动对拍，漏改一处直接列出来（顺带查"充电脚本门限低于电源 CV"）；
5. 重跑阶段 3~4。

### 全流程一页速查

```bash
# ── 阶段 1 采集（两个终端）──────────────────────────
python soc_record.py --out stair1.csv          # 终端 B：先开，录 5min 基线
python soc_bench.py                            # 终端 A：向导 → 程控 → 方向 → 十档 (~2.8h)
# 跑完: copy load_segments.json stair1_plan.json

# ── 阶段 2 分析（终端 B 先 Ctrl+C 停采集）───────────
python soc_bench.py stair --csv stair1.csv      # 参数自动从计划文件取

# ── 阶段 3 EKF 调参闭环 ────────────────────────────
python test/kalman_tune.py --csv stair1.csv --refs stair1_stair.csv
#   → 改 bms_config.h 的 EKF 参数 → 烧录 → 下轮用 --param 校验

# ── 阶段 4 SOH 验证 ───────────────────────────────
python soh_learn.py   --csv stair1.csv --refs stair1_stair.csv
python soh_mcu_sim.py --csv stair1.csv --refs stair1_stair.csv
```

## 5. 固件 ↔ PC 常量同步表

**这些值在固件和 PC 脚本里各存了一份，改任何一处都必须同步改另一处**，
否则标定结果与板子行为会悄悄错开。
固件的唯一配置入口是 `../算法库/bms_config.h`。

| 内容 | 固件位置（`bms_config.h`） | PC 位置 |
| --- | --- | --- |
| OCV 表（11 点 mV） | 标定表组 | `soc_load.py` `DEFAULT_OCV_MV`、`soc_bench.py` `STAIR_OCV_MV`、`soh_learn.py` `OCV_MV`、`kalman_tune.py` `OCV` |
| R0 表（11 点 mΩ） | 标定表组 | `soh_learn.py` `R0_CAL`、`kalman_tune.py` `R0` |
| R1 表（11 点 mΩ） | 标定表组 | `soh_learn.py` `R1_CAL`、`kalman_tune.py` `R1` |
| τ 表（11 点 s） | 标定表组 | `soh_learn.py` `TAU_S`、`kalman_tune.py` `TAU` |
| 标称容量 3350 mAh | `SOC_CAPACITY_NOMINAL_MAH` | `soc_bench.py` `STAIR_CAPACITY`、`soh_learn.py` `Q_NOM_MAH`、`kalman_tune.py` `CAP` |
| 静置电流门限 20 mA | `SOC_IDLE_CUR_MA` | `soc_bench.py` `IDLE_MA`、`soh_learn.py` `IDLE_MA`、`kalman_tune.py` `IDLE_MA` |
| EKF 参数 `q_soc/q_vrc/R` | EKF 参数组 | **不用同步** —— `kalman_tune.py` 的 `fw_defaults()` 直接从 `bms_config.h` 现读（上位机「填固件现值」按钮走这条路） |
| SOH 判据全套 | SOH 判据组 | `soh_learn.py` 顶部常量块（**`soh_mcu_sim.py` 启动时自动比对**） |

**这张表有脚本帮你对**（从源码文本抽表，不 import，所以不挑环境）：

```bash
python test/check_consts.py          # 在 脚本/ 或 脚本/test/ 下都能跑
python test/check_consts.py --quiet  # 只打印问题数
```

它逐项比对（共 11 段）：OCV / R0 / R1 / τ 四张表（PC 四个副本 ↔ 固件
`bms_config.h` 的 `SOC_*_25C_*` 宏）、标称容量、静置门限、stair 判据、
**上位机模式表 vs `soc_load.py` 的 `MODES`**、档位计划格式串、
**循环默认值 vs `soc_bench.CYCLE_*`**、跨设备互锁（含"先关伙伴再开自己"的
**行号**顺序不变量）、三模式与腿执行器 `LEG_RUNNER`，外加形态检查
（点数 / OCV 单调 / 非负）。退出码 0 = 全一致。

> `soh_mcu_sim.py` 启动时也会做一次 SOH 判据的三方比对并报警 ——
> 那是运行期校验，`check_consts.py` 是静态校验，两者互补。
> 改表之后仍建议**跑一次阶段 2**，看 OCV-SOC 表是否与预期一致。

## 6. 常见问题

**Q：CSV 里 `SOH_0p01 / Q_mAh / R0_mohm` 三列是空的？**
A：板上固件上报的字段较少。烧录完整 8 列版本的固件即可；老数据仍可分析，只是这几列缺失。

**Q：`soc_record.py` 看不到数据 / 全是乱码？**
A：`chcp 65001` 先切 UTF-8；再确认波特率（MCU 侧 115200）。
若一行都收不到，多半是选错了 COM 口。

**Q：`soc_load.py` 找不到设备？**
A：确认源/载 RS232 口已插好、设备开机。脚本会遍历串口发 `*IDN?`；
实在认不出就手动 `--port COMx`。**同时接了一源一载**（一个充电一个放电）时必须
显式给 `--port`，自动探测只会认到第一个应答的。

**Q：`soc_bench.py stair` 的容量 / 起始 SOC 是从哪来的？**
A：按 **命令行 > 档位计划文件 > 标称值/电压反查** 三级取，屏幕上会写清每级用了什么。
要锁死就把三个参数都显式写上。计划文件是 `soc_load.py` 的 `*_plan.json`，
改名成 `<record 前缀>_plan.json` 放在同目录就会被自动认到。

**Q：充电数据跑 `stair` 报"OCV 表非单调"？**
A：老版本按**时间顺序**判单调，充电时 SOC 往上走，必然误报 —— 现在改成
**按 SOC 排序后判**。若还报，说明表本身真有问题，或者 `--init-soc` 反查错了。

**Q：能不能用充电曲线标定电池参数？**
A：能，而且不需要改算法 —— 数值框架本来就方向无关（见 [3.3④](#-stair--多档周期分析主力)）。
三点注意：① 充电侧默认只跑到 80 %，再往上进 CV 电流不可控；
② 充/放 OCV 有**迟滞**，标出的是"充电方向的表"，别直接替换放电表；
③ 反过来"CC-CV 进 CV 后电流衰减到 C/20"是**唯一确定的 100 % 锚点**，
拿它校 `--init-soc` 比任何默认值都靠谱。

**Q：`soc_bench.py stair` 说"只检测到 N 个档位"？**
A：档位没跑全（中途中止）或 `--i-off` 阈值太严。先用 `--expect 0` 关掉提示，
再微调 `--i-on/--i-off`。

**Q：`soh_mcu_sim.py` 报警"常量不一致"？**
A：`bms_config.h` 和 `soh_learn.py` 顶部的判据常量被改了一边。按[第 5 节](#5-固件--pc-常量同步表)同步。

**Q：`--scale 0.8` 学到的是 3350 而不是 2680？**
A：说明触发条件没满足（ΔSOC/ΔQ 不够）或 OCV 表把误差吸收了。
先看 `soh_learn.py` 打印的锚点对数与 `SOH_rel = Q/Q_ref`（比值里 OCV 误差抵消）。

**Q：绝对精度不够（比如新电池只学到 ~96 % 标称）？**
A：**这是 OCV 表本身的误差，不是学习器的问题**（平台区 ~8 mV ≈ 0.82 % SOC）。
正解是重标 OCV 表（满充 4.20 V CV→C/20，0.2C 慢放到 2.8 V），
只看老化趋势时用 `SOH_rel` 即可。

**Q：想要并行/批处理，不想交互？**
A：所有脚本的交互参数都能用命令行补齐（`--port / --baud / --csv` 全给了就零交互）。
`soc_load.py` 另有 `--yes`：缺的参数一律取缺省值，且跳过"回车开始"确认（上位机用它；
真实充放电的确认改由界面上的确认框承担）。

## 7. 图形界面（exe）

不想敲命令就用 `bms_gui.py`：把上面这套脚本包成一个窗口程序，六个页签对应
标定的实际流程。

```bash
python bms_gui.py            # 源码直接跑
python build_exe.py          # 打包 -> ../上位机/锂电池上位机.exe
```

| 页签 | 对应脚本 | 说明 |
| --- | --- | --- |
| ① 采集监视 | `soc_record.py` | 采集循环重写了一遍（交互式的套命令行反而难用），大字号实时值 + CSV |
| ② 在线调参 | `bms_tune_proto.py` | bms_tune 协议，见下 |
| ③ 控载 | `soc_load.py` / `soc_bench.py cycle` | 先选**模式**（拉载 / 充电 / 循环，见下）→ 填参数 → 填串口 → 确认框 → 后台跑；带「紧急停止」「识别设备（*IDN?）」「命令方言」三个按钮 |
| ④ 分析 | `soc_bench.py` | `fit` / `stair` 都是同一个脚本的两种子命令；容量 / 起始 SOC / 期望档数**可留空**，脚本会自己找档位计划 |

**界面上三处约定**（省得第一次用到处找）：

- **每页顶部那行蓝字 = 「本页做什么 · 下一步去哪」**，照着走就是标定的实际顺序
  （① 采集 → ③ 控载 → ④ 分析 → ② 写回板子）。
- **长段说明收在「?」里**：页面上只留一行摘要，点旁边的「?」弹窗看全文 ——
  安全保护 6 项、温度解耦、三级自动定、EKF 那套 `0x18`/`0x19` 的读写边界都在里面。
  顶栏右上角那个「?」是工具目录 + 「改哪份脚本才需要重新打包」。
- **串口叫法统一**：① ② 页叫「串口」；③ 页单腿跑叫「本机串口」，循环跑换成
  「放电口（负载）」/「充电口（电源）」（两个都得填）。① 页「输出 CSV」的默认名带
  时间戳（`soc_data_0914-1235.csv`），连采两次不会互相覆盖。

**③ 控载页的三种模式**（同一个页面，切模式会换参数区、按钮文案和串口标签）：

| 模式 | 实际走 | 说明 |
| --- | --- | --- |
| 拉载（电子负载） | `soc_load.py` | 一次一个方向：按档位"恒流放 → 断开静置"走到终止 SOC |
| 充电（可编程电源） | `soc_load.py --charge` | 同上，换方向；门限变成端压上限，且**必须低于**电源 CV |
| 循环（多轮充放） | `soc_bench.py cycle` | 逐腿调度"放 → 充"交替多轮（见 [3.3 ⑤](#-cycle--多轮充放循环老化--一致性)）；两个串口都要填 |

模式一换，表单立刻跟着变：**单腿参数**（起始 / 终止 SOC、电流、档位分布、门限、电源 CV、空载联调）和**循环参数**（轮数、窗口两端、两条腿各自的电流与门限、两边方言、跑不满怎么办、先预览）只显示当前模式要用的那一组，不用对着用不上的框猜。

**串口怎么填**（两个框都是"下拉 + 可手输"，各带一个「刷新」）：

- **留空、或选「（自动探测）」** = 交给脚本自己探（脚本里绝不写死某个 COM）；
- 下拉里是枚举到的串口（`COMx` + 描述），也可以**直接手输** `COM12`；
- 点工具栏的 **「识别设备（*IDN?）」** 会逐个口发 `*IDN?`（只读，不改设备状态），
  认出来的口在下拉里标 `★` 并显示设备身份 —— 两台设备同时插着时，一眼就能分辨
  哪台是负载、哪台是电源，不用去设备管理器猜；
- **循环模式下两个口都必须填**：每腿开跑前要先关另一台（跨设备互锁），缺一个口时
  那一腿只能自动探测，而两台同插时会挑错，互锁就无从建立 —— 界面会直接拦住。

### 7.1 分析类脚本是"包进来跑"，不是"拉子进程"

`bms_gui.py` **不重写**任何分析脚本：它用 `importlib` 把同目录的脚本加载进来，
把参数拼成 `argv`、把 `stdout` 重定向到界面日志，然后调它的 `main()`。
好处是命令行版和界面版永远同一套逻辑，不会两边漂移。

代价有三条，改脚本时要记住：

1. 脚本里**不能有 `input()`** —— 界面里没有控制台可敲。所有交互参数必须能由
   命令行给全（`soc_load.py --yes` 就是为此加的）。
2. 脚本是在**同一个进程**里执行的，所以 `numpy` / `matplotlib` / `pyserial`
   必须在打包时 `--hidden-import` 进去（`build_exe.py` 里已经列了）。
   PyInstaller 的静态分析看不到这些 import——它们藏在数据文件里的脚本中。
3. **循环模式**要在本进程里逐腿调 `soc_load.py`：`soc_bench.py cycle` 默认是给每腿
   **另起一个 python 进程**，可打包成 exe 之后 `sys.executable` 指向 exe 自己，另起
   进程只会又弹一个界面出来。所以界面把 `soc_bench.LEG_RUNNER` 换成"在本进程里调
   `soc_load.py`" —— 腿序 / 窗口 / 互锁 / 停跑判据仍是同一份编排代码，只换了执行方式
   （`check_consts.py` 第 [11] 段看着这条）。命令行那边不受影响，仍是真的子进程。

### 7.2 在线调参页

界面**从协议命令表自动生成**：`bms_tune_proto.py` 的 `COMMANDS` 有 34 条，
命令树就长 34 条；`Cmd.down` 里几个 `Field`，右边就铺几个输入框。
加一条命令只改协议模块，界面不用动。

表里同时带着**给人看的说法**（`Cmd.label` / `Field.label` / `Cmd.needs`），
所以界面上出现的是「读一个标定点」「温度点序号」，不是 `RD_CAL_POINT`、`ti`；
命令码和协议名退到右侧那行小字里，对协议手册时照样一眼能找到。
带编译开关依赖的命令（掉电保持那几条）在列表里是橙色的，选中后会写清为什么。

除了通用命令面板，标定表 / R0 / SOH 三个批量操作有专用编辑器：

| 子页 | 内容 |
| --- | --- |
| 单条命令 | 34 条按用途分组 + 中文搜索框；点一条右边出参数表单，填工程值（mV / mΩ / s / mAh / °C），CRC 自动算，要填几项直接标在列表里 |
| 标定表 | 温度点下拉 × 4 张表 × 11 点可编辑网格；「读整包 → 改 → 写回整包」，带读回校验 |
| R0 活跃值 | 11 个输入框 + 读/写全部、读/写第 N 点 |
| SOH | 读摘要 / 读 120 B 参数块（逐字段展开，含充电方向 R0 与累计充放电）/ 写回 / 读累计与循环 / 清累计与循环 / 导出导入 bin / 清学习值 |
| 容量 / 温度 / 落盘 / 原始帧 | 容量写后自动读回确认（看钳位）、温度、**读工况折算系数**（温度 / 倍率修正后的可用容量）、立即存 Flash / 读保存状态、手发任意帧 |

几条要点：

- **维度不硬编码**：温度点数、表数、SOC 点数、整包字节数全部由 `INFO` 命令问板子，
  换一块点数不同的板子界面自动跟着变。
- **原始帧页**可以发协议表里没有的命令码（用来看固件返回 `rc=3` 未编译）。
- 标定表改了 5 °C 而当前温度是 25 °C 时，「活跃表」不会变 —— 这是**温度解耦**，不是没生效。

### 7.3 图表面板：跑完的图直接显示在窗口里

④分析 / ⑤SOH / ⑥EKF 三页是**上半个图、下半个日志**，中间横条可以拖。
脚本一跑完，它落盘的那张 PNG 就自动进面板 —— 不用去文件夹里找，也不用切看图软件。

| 脚本 | 自动显示的图 |
| --- | --- |
| `soc_bench.py fit` | `*_fit.png`（RC 拟合） |
| `soc_bench.py stair` | `*_stair.png`（R0/R1/tau/OCV/SOC 汇总，**默认显示这张**）<br>+ `*_stair_timeline.png`（充/放时序，按 ▶ 翻） |
| `soh_learn.py --plot` | `*_soh.png`（R0 学习结果） |
| `test/kalman_tune.py --plot` | `*_ekf.png`（SOC 轨迹 / 误差 / 电流电压三连图） |

面板上的按钮：

- **◀ ▶** 换图，标题右边有 `[2/2]` 这样的位置提示
- **适应窗口** 整张缩进可见（只缩不放 —— 放大超过 1:1 只会糊，没意义）
- **1:1 / + / −** 看细节；**Ctrl + 滚轮**也能缩放，普通滚轮上下滚
- **双击图** 弹一个独立大窗（`Esc` 关）
- **另存为…** 拷一份到别处；**外部打开** 交给系统看图器

标题栏一直写着 `文件名  宽×高  显示百分比  [第几张/共几张]`，
截图贴报告时能说清是哪张、缩了多少。

> 缩放靠 Pillow。没装也能用，但只能整数倍缩小、画质粗，标题里会提醒一句。
> `pip install -r requirements.txt` 即可。

### 7.4 打包形态

`build_exe.py` 产出：

```
上位机/
    锂电池上位机.exe      双击即用
    _internal/           解释器 + numpy + matplotlib + tcl/tk
    tools/               脚本本体，exe 优先用这一份，改了立刻生效
    读我.txt             给不写代码的人看的一页说明
```

默认是 `--onedir`（一个文件夹），**不是单文件**。原因很实在：

| 形态 | 启动耗时（实测） | 说明 |
| --- | --- | --- |
| `--onedir`（默认） | **2.5~3 s**（刚打包完首次启动要读盘，会顶到 3 s 出头） | 起一次就完事 |
| `--onefile` | 冷启 18 s / 热启 12.5 s | 每次都要把 ~130 MB 解压到 `%TEMP%`，再被 Defender 扫一遍 |

这工具是要反复点开的，所以默认给快的那个。真要单文件（比如丢 U 盘上）：

```bash
python build_exe.py --onefile      # 包内会多塞一份 tools/ 作兜底
```

两种形态都不挡改脚本：只要 exe 旁边有 `tools/` 目录，就优先用旁边那份
（没装 Python 的机器也一样跑，因为解释器在 `_internal/` 里）。

> 分析产物（png / csv）落在**你选的数据 CSV 旁边**，不在 `上位机/` 里。
