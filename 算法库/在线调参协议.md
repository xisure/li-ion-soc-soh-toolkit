## 1. 这份文档讲什么

标定表、容量、R0、SOH 学习结果原先只能改 `bms_config.h` 再重新烧录 —— 做实验一天烧十几次，
不同电芯的 OCV 表没法现场切换。`bms_tune` 把它们做成**运行时可读写**；SOC 运行态与
**EKF 的 8 个参数**（原先也是编译期宏）同样可以在线读写，见 §6.5；
**累计充放电 / 循环次数 / 充电方向 R0 / 工况折算系数**见 §6.6。

**库里没有一行 UART 代码**，这是刻意的。一旦 `#include` 某个厂家的 UART 头文件，这个库就只能在
那一家上用。本模块只定义"字节流怎么成帧、成帧后调哪个接口"，收发字节交给工程侧：

```
  PC 上位机
     │  字节流
  UART / USB CDC / CAN / 蓝牙透传      ← 工程侧负责（本文档 §9 给接线代码）
     │
  bms_tune 协议层                      ← 本文档规范的对象
     │
  标定表 / 容量 / R0 / SOC / EKF / SOH   ← bms_cal / soc / soh 已有能力
     │
  bms_nvm 掉电保持                      ← SOH 参数落盘；标定表与 EKF 参数不落盘（见 §6.2 / §6.5）
```

因此同一套协议能挂在任何能收发字节的通道上，换通道不改库。

## 2. 五分钟接线

下位机三步（完整说明见 §9）：

```c
static ring_t g_rx;                              /* 你自己的接收环形缓冲 */

void UARTx_IRQHandler(void)                      /* 中断里只塞字节，不要解析 */
{
    if (RXNE) ring_put(&g_rx, USART_ReceiveData());
}

int main(void)
{
    BMS_TUNE_SetTx(uart_putc);                   /* 1. 注册"发一个字节" */
    for (;;)
    {
        while (ring_avail(&g_rx))
            BMS_TUNE_Feed(ring_get(&g_rx));      /* 2. 主循环里解析 + 执行 */
        /* ... 其他任务 ... */
    }
}
```

3. `bms_config.h` 的 `[9]` 组把 `BMS_USE_TUNE` 改成 `1`，重新编译。

上位机最小实现（Python）：

```python
import struct

def crc16(d):
    crc = 0xFFFF
    for b in d:
        crc ^= (b << 8)
        crc &= 0xFFFF
        for _ in range(8):
            crc = (((crc << 1) ^ 0x1021) & 0xFFFF) if (crc & 0x8000) else ((crc << 1) & 0xFFFF)
    return crc

def frame(cmd, pay=b''):
    body = struct.pack('<HB', len(pay), cmd) + pay
    return b'\xAA\x55' + body + struct.pack('<H', crc16(body))
```

## 3. 帧格式

### 3.1 帧结构（上行下行同构）

```
偏移    长度   字段
0       1      SOF0    0xAA
1       1      SOF1    0x55
2       2      LEN     payload 字节数（u16 小端）
4       1      CMD     命令字
5       LEN    PAYLOAD
5+LEN   2      CRC16   u16 小端

帧总长 = 7 + LEN
```

最短帧是 7 字节（LEN = 0，只有命令没有数据）。

### 3.2 CRC16-CCITT

| 参数 | 值 |
|---|---|
| 多项式 poly | `0x1021` |
| 初值 init | `0xFFFF` |
| 输入反射 | 无 |
| 输出反射 | 无 |
| 输出异或 | `0x0000` |

即标准 **CRC-CCITT-FALSE**。**关键：CRC 覆盖偏移 2 .. 4+LEN，也就是 `LEN + CMD + PAYLOAD`，
不含 `AA 55` 前导。** 这是最常见的对接错误来源。

自检向量（务必用它对一遍你的实现）：

| 输入 | 期望 |
|---|---|
| `"123456789"` | `0x29B1` |
| `00 00 00` | `0xCC9C` |
| `05 00 03 01 01 05 D2 04` | `0xB3B4` |

C 参考实现（`bms_tune.c` 里的版本，位运算，无表）：

```c
static uint16_t crc16_up(uint16_t crc, uint8_t b)
{
    uint8_t i;
    crc ^= (uint16_t)((uint16_t)b << 8);
    for (i = 0u; i < 8u; i++)
    {
        if (crc & 0x8000u) crc = (uint16_t)((uint16_t)(crc << 1) ^ 0x1021u);
        else               crc = (uint16_t)(crc << 1);
    }
    return crc;
}

/* 整帧校验: 初值 0xFFFF, 依次喂 LEN低 LEN高 CMD PAYLOAD... */
```

> CRC 参数与 `bms_nvm.c` 落盘用的是**同一套**，所以上位机只需一份 CRC 实现。
> 代价是库里两份 static 函数（为 20 行代码多拉一个文件不划算），**改一处必须改两处**。

### 3.3 为什么 LEN 用 u16 不用 u8

标定表整包是 `3 × 4 × 11 × 2 = 264` 字节，超过 255，u8 装不下。
用 u16 也顺便让将来加温度点不用改帧格式。

### 3.4 帧同步与自恢复

状态机靠 `AA 55` 定界。三种脏数据都能自恢复，不需要上位机做任何配合：

| 情况 | 行为 |
|---|---|
| 帧前有垃圾数据（`00 13 FF 7E` 等） | 一直丢弃到出现 `AA 55`，最多丢一帧 |
| 重复前导 `AA AA 55` | 收到 SOF0 后又收到 SOF0 会**停在"等 SOF1"**，不退回起点 |
| 半截帧（发一半断了） | 下一帧起重新同步；也可用 `BMS_TUNE_Reset()` 主动打断 |

CRC 错的帧**静默丢弃，不应答**（错误计数 +1）。这意味着上位机**不能靠错误码判断 CRC 错**，
只能用超时重传 —— 见 §8。

### 3.5 长度限制

`BMS_TUNE_RX_MAX` 默认 `BMS_CAL_BYTES + 8 = 272`。超过这个长度的帧会被判"不可能的帧"
直接丢弃并计数，**不产生应答**。RAM 极紧时可以调小，代价是超长的整包命令失效
（单点读写命令只有几个字节，不受影响）。

应答**复用接收缓冲**，所以不存在独立的 264 B 应答缓冲 —— 这是刻意的，省 264 B RAM。

## 4. 应答与状态码

应答帧格式完全同构，只有两处不同：

1. `CMD` 改成 `CMD | 0x80`（所以**命令字最高位必须为 0**，取值范围 `0x00~0x7F`）
2. **所有应答的 `payload[0]` 都是状态码 `rc`**

| rc | 宏 | 含义 | 上位机该怎么做 |
|---|---|---|---|
| 0 | `BMS_TUNE_OK` | 成功 | 读命令继续解数据字段 |
| 1 | `BMS_TUNE_EBADARG` | 参数越界（温度点 / 表号 / SOC 点序号 / 值域不对） | 这是**你的 bug**，别重试 |
| 2 | `BMS_TUNE_EBADLEN` | 下行 payload 长度不是该命令期望的值 | 这是**你的 bug**，别重试 |
| 3 | `BMS_TUNE_ENOSUP` | 该功能未编译进库（如 `BMS_USE_NVM=0` 时的 SOH 块和落盘命令） | 换命令或改编译开关 |
| 4 | `BMS_TUNE_ECRC` | **不会作为 rc 发出** —— CRC 错的帧根本不产生应答，只内部计数 | — |

`rc != 0` 时应答 payload **只有 1 个字节**（就是 rc 本身），后面不跟数据。

<a id="5"></a>
## 5. 数据编码约定

| 约定 | 说明 |
|---|---|
| 字节序 | **全部小端**（低字节在前）。多字节整数逐字节拼，不做结构体 memcpy |
| 有符号 | 温度用 `i16`，单位 **0.1 °C**（250 = 25.0 °C，−100 = −10.0 °C） |
| SOC / SOH | `u16`，单位 **0.01 %**（10000 = 100.00 %） |
| 电压 | `u16`，单位 **mV** |
| 内阻 | `u16`，单位 **mΩ** |
| 容量 | `u32`，单位 **mAh** |
| 时间常数 | `u16`，单位 **s** |
| 浮点 | `f32`，**IEEE-754 单精度，4 字节小端**。只有 EKF 的 8 个参数用它（§6.5） |

`f32` 是唯一一种"不是定点整数"的字段。为什么 EKF 参数不折算成定点：它们的取值范围跨
13 个数量级（`p_min` 1e-4 ~ `r_v` 1e6），折算成定点要么牺牲小值分辨率，要么得给每个参数
单独定标；而 PC 侧本来就是浮点（`kalman_tune.py`），折算反而在两端各引入一次误差。
IEEE-754 单精度在两边都是原生的，直接按位传最省事。

> `f32` 的值**不做任何缩放**：写 0.002 就是 0.002，不是 20。上位机界面里的
> 「单位」列只是说明这个数是什么物理量，输入框里填真实值。

标定表三个维度索引：

| 符号 | 含义 | 取值 |
|---|---|---|
| `ti` | 温度点序号 | `0~2`，对应 `BMS_CAL_TEMP_DC` = {5.0, 25.0, 45.0} °C |
| `tbl` | 表号 | `0` OCV / `1` R0 / `2` R1 / `3` τ |
| `idx` | SOC 点序号 | `0~10`，对应 0%、10%、…、100% |

**用 `0x01 INFO` 拿到这些维度，不要硬编码。** 改了 `bms_config.h` 里的温度点个数，
`cal_bytes` 会变，硬编码 264 的上位机会静默错位。

确认对端在不在、协议版本对不对。**接上串口第一件事就是发它。**

|---|---|---|
| 0 | 1 | rc |

维度自检。上位机**必须**靠它自适应。

下行：无

### 6.2 标定表（出厂基准，不含老化量）

标定表是**三层**：`ti`（温度）× `tbl`（表）× `idx`（SOC 点）。
改它改的是"出厂基准"，不含 SOH 学到的老化量 —— 那是 §6.3 的 R0 活跃值。

#### `0x02` RD_CAL_POINT

下行（3 B）：`ti` u8，`tbl` u8，`idx` u8
上行（3 B）：`rc`，`v` u16

#### `0x03` WR_CAL_POINT

下行（5 B）：`ti` u8，`tbl` u8，`idx` u8，`v` u16 小端
上行（1 B）：`rc`

#### `0x04` RD_CAL_ALL / `0x05` WR_CAL_ALL

264 B 整包，**布局固定**：

```
offset = ((ti * tbl_n + tbl) * soc_n + idx) * 2      # 每点 u16 小端
```

即外层温度点、中层表、内层 SOC 点。`RD_CAL_ALL` 上行是 `rc + 264 B = 265 B`；
`WR_CAL_ALL` 下行就是裸的 264 B（不含 rc）。

> 上位机流程：先 `RD_CAL_TEMPS` 确认温度点 → `RD_CAL_ALL` 读全部 → 改你要改的点 →
> `WR_CAL_ALL` 整包写回。**不要自己拼一套新表**，读改写才不会漏掉你没标定的温度点。

#### `0x06` CAL_RESTORE

恢复出厂标定表（回 `bms_config.h` 里的编译期默认值）。**掉电也会回到这个值** —— 见下。

#### `0x07` RD_CAL_TEMPS

上行（7 B）：`rc` + `temp_n` × `i16`，单位 0.1 °C。

#### `0x08` RD_TEMP / `0x09` WR_TEMP

读 / 强制设置当前温度（`i16`，0.1 °C）。调试时用它跳过温度传感器，直接看某个温度下的插值结果。
注意算法主循环每 200 ms 会调 `BMS_CAL_Update()` 用传感器真实值覆盖，所以**强制温度只在
主循环没跑时有效**（仿真、单步调试），或者你临时注掉 `BMS_CAL_Update()`。

#### `0x0A` RD_CAL_ACTIVE

读**当前温度插值出来的活跃表** —— 算法实际在用的那一张。调试必备：
改了 5 °C 的表但当前 25 °C，活跃表不会变，这不是没生效，是温度解耦。

上行（89 B）：`rc` + 88 B，布局 `offset = (tbl * soc_n + idx) * 2`（只有表 × SOC 点两层）。

#### 标定表为什么不落盘

标定表（264 B）**不进 `bms_nvm`**。下位机改完表掉电就回出厂值，上位机是权威源，
上电后由它重新下发。理由：

- 落盘要 `264 + 12 = 276 B`，**超过 CH32X035 的单个 256 B 页**，得改成多块 / 多区域，
  `bms_nvm` 的接口（"槽 = 一个独立擦除单元"）要跟着扩；
- 标定表改动频率极低（标定一次管几个月），为它耗 Flash 寿命不划算；
- 上位机本来就要存原始标定数据，让它当权威源不会丢东西。

代价：MCU 脱机不能保持标定。真需要时扩展 `bms_nvm` 加第二存储区即可，**协议层不用动**。

### 6.3 R0 活跃值（出厂基准 + 老化增量）

这是**算法真正用的** R0：`活跃值 = 当前温度的出厂基准 + SOH 学到的老化增量`。
`0x02/0x03` 改的是基准，这里改的是基准+增量的合成结果。

#### `0x10` RD_R0

下行（1 B）：`idx`
上行（3 B）：`rc`，`v` u16

#### `0x11` WR_R0

下行（3 B）：`idx` u8，`v` u16 小端
上行（1 B）：`rc`

**传的是绝对值**，库内部换算成"相对当前温度基准的增量"。所以先把温度切到目标温度
（或确认当前温度），再写，否则增量会算在错误的基准上。

#### `0x12` RD_R0_ALL / `0x13` WR_R0_ALL

22 B = 11 点 × 2 B。`RD_R0_ALL` 上行是 `rc + 22 B = 23 B`；`WR_R0_ALL` 下行是裸 22 B。

批量写用整包，比 11 次单点快，也避免"写了一半掉电"。

> 这里读写的都是**放电方向**那张表。充电方向另有一张，用 `0x26` / `0x27`，详解见 §6.6。

---

### 6.4 容量

#### `0x14` RD_CAP

上行（5 B）：`rc` + `mAh` u32

#### `0x15` WR_CAP

下行（4 B）：`mAh` u32 小端
上行（1 B）：`rc`

**库不做"这个值合理吗"的猜测，只做钳位**：越界值被 `soc.c` 钳到
`[SOC_CAP_LO_PCT, SOC_CAP_HI_PCT] × 标称容量`，默认 `[50%, 110%] × 3350 = [1675, 3685]` mAh。
所以写 999999 得到 3685、写 100 得到 1675，**返回 `rc = 0` 不代表你写的值原样生效** ——
写完用 `RD_CAP` 读回确认。

### 6.5 SOC 运行态与 EKF 参数

> 这一节是**在线调参的主力**：EKF 的 8 个参数原先全是 `bms_config.h` 里的编译期宏，
> 想试一组参数就得重编固件。现在改运行期变量，写下去下一帧就生效。

#### `0x16` RD_SOC

读 SOC 的**运行态**：估计值、积分基准、累计电荷，外加 EKF 的极化与协方差。

下行：无

上行（22 B）：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | rc | |
| 1 | 2 | `soc01` u16 | SOC 估计值，0.01 % |
| 3 | 2 | `base01` u16 | **积分基准**，0.01 % |
| 5 | 4 | `coul_mah` i32 | 自基准起累计的电荷，mAh，**放电为正** |
| 9 | 1 | `flags` u8 | bit0 = EKF 已建立（其余位保留） |
| 10 | 4 | `kf_vrc` f32 | EKF 极化电压，mV（未建立时 0） |
| 14 | 4 | `p11` f32 | SOC 方差 |
| 18 | 4 | `p22` f32 | 极化方差 |

```python
soc01, base01 = struct.unpack_from('<HH', pay, 1)
coul, = struct.unpack_from('<i', pay, 5)
flags = pay[9]
vrc, p11, p22 = struct.unpack_from('<fff', pay, 10)
```

`soc01 / base01 / coul_mah` 三个一起看能把偏差**拆成两半**：

```
SOC ≈ base01 - coul_mah × 10000 / 容量(mAh)
```

- `base01` 变、`coul` 小 → 刚做过 OCV 重同步或人工对齐；
- `base01` 不动、`coul` 一直长而 SOC 偏 → 安时积分在漂（容量或电流标定）。

`p11 / p22` 是滤波器自己报的"我有多确定"。**这两个数是判断 EKF 有没有收敛的唯一入口** ——
调完参数想看效果，别看 SOC 有没有跳，看 P11 有没有在一个合理量级上趋稳。

#### `0x17` WR_SOC

把一个**已知** SOC 强制对齐进去（现场标定、或拿表对过之后纠偏）。

下行（2 B）：`soc01` u16，0.01 %，合法 `0 ~ 10000`
上行（1 B）：`rc`

库内部做四件事：重建积分基准 / 清零累计电荷 / **直接把 EKF 的 SOC 置成该值** / 重新开始静置计时。

两个容易误解的点：

- **为什么不按端电压反查 OCV 表来对齐？** 带载时端电压 = OCV − I·R0 − 极化，查表值系统性偏低。
  人工给的已知值比带载端压可靠得多。
- **设完不会一直保持**：静置满 `SOC_IDLE_MS`（默认 900 s）后，重同步仍会把 SOC 拉向 OCV 表读数。
  这是有意的（静置态 OCV 是唯一真值），不是命令没生效。区别只是：设过之后走"半衰限幅"
  （每轮最多动 `SOC_RESYNC_MAX_01`），而不是首次重同步那种一次性覆盖。

> **WR_SOC 不影响 SOH 学习。** 容量学习的两个 OCV 锚点记的是 `SOC_VoltageToSoc01(静置端压)`，
> 与估计器的 SOC 无关；ΔQ 也是库内部独立累计的。所以不存在"把正在进行的静置窗口作废"这回事，
> 调完 SOC 不用等一个完整的静置周期再开始学容量。
>
> 附带结论：**别指望 WR_SOC 能修 SOH**。容量学得准不准取决于 OCV 表本身（见 §6.2 与 README §9），
> 人工对齐的只是估计器。

#### `0x18` RD_EKF

读 EKF 的 8 个参数现值。

下行：无

上行（33 B）：`rc` + 8 × `f32`，**顺序固定**：

| 序号 | 名字 | 对应 `bms_config.h` 宏 | 出厂值 | 单位 | 合法区间（开区间） |
|---|---|---|---|---|---|
| 0 | `q_soc` | `BMS_EKF_Q_SOC` | 0.001 | %²/帧 | `1e-9 ~ 1.0` |
| 1 | `q_vrc` | `BMS_EKF_Q_VRC` | 0.5 | mV²/帧 | `1e-9 ~ 1e4` |
| 2 | `r_v` | `BMS_EKF_R_V` | 10.0 | mV² | `1e-9 ~ 1e6` |
| 3 | `p0_soc` | `BMS_EKF_P0_SOC` | 10.0 | %² | `1e-9 ~ 1e4` |
| 4 | `p0_vrc` | `BMS_EKF_P0_VRC` | 400.0 | mV² | `1e-9 ~ 1e6` |
| 5 | `res_max_mv` | `BMS_EKF_RES_MAX_MV` | 250.0 | mV | `1e-6 ~ 1e5` |
| 6 | `s_min` | `BMS_EKF_S_MIN` | 1e-6 | mV² | `1e-12 ~ 1.0` |
| 7 | `p_min` | `BMS_EKF_P_MIN` | 1e-4 | — | `1e-12 ~ 1e4` |

```python
vals = struct.unpack_from('<8f', pay, 1)
```

顺序与固件 `soc.h` 的 `soc_ekf_param_t` 一一对应，也与会话示例里的字节序一致。

#### `0x19` WR_EKF

整组写 8 个参数。

下行（32 B）：8 × `f32` 小端，顺序同上，**不含 rc**
上行（1 B）：`rc`

**必须先 `RD_EKF` 读整组、改其中你要改的、再整组写回。** 两个理由：

1. 没有"单参数写"这个形态 —— 只想改 `q_soc`，其余 7 个也得原样带上（上位机的
   `Client.ekf_write_subset()` 就是干这个的）；
2. `rc = 0` 只代表**整组都通过了检查**，不代表这些值就是好参数。

**两趟校验，一个越界整组不写**：库内先用 `SOC_EkfParamOk()` 把所有值过一遍，只要有一个
出界就直接回 `rc = 1`，一个字节都不写进去。这样不会出现"写进去一半"的参数组 ——
半组状态在板子上表现为"行为怪但语法没错"，最难查。

固件只挡"明显写错"的值：非正数 / NaN / 量级离谱（比如把 `r_v` 填成 1e30，会让卡尔曼增益恒为 0）。
**参数好不好不在固件里判** —— 那是一组参数跑一遍 PC 端回放（`脚本/test/kalman_tune.py`）的事。

#### `0x1A` EKF_RESET

把滤波器打回"刚建立"的状态：极化电压清零、协方差回 `p0_soc` / `p0_vrc` 初值。
**保留当前 SOC 估计，不重猜。**

- 为什么改完 `p0_*` 要发一次这个：`p0_*` 只在 EKF 建立 / 复位那一次用，平时写进去不生效。
- 为什么不重猜 SOC：调参的人要的是"用新参数重新收敛"，不是"按当前（多半带载的）端电压重算
  SOC"。按 OCV 重新对齐是静置重同步的职责。
- EKF 还没建立时，起点取"基准 + 积分"的当前值（与 `SOC_GetPercent01()` 的回退路径同值），
  所以复位前后显示不会跳。

#### EKF 参数为什么不落盘

和标定表同一个理由，但更彻底：**上位机与 `bms_config.h` 是权威源**，板子掉电就回
`bms_config.h` 的编译期默认值。

- 参数定下来之后应该写进 `bms_config.h` 重编（那才是"产品状态"），`bms_tune` 只是实验通道；
- 8 个 `f32` = 32 B 看着不多，但一旦落盘就要加版本号、加兼容处理，还要和"标定表不落盘"
  这条规则区分开，复杂度全在上位机侧；
- 调参是个高频动作（一天几十次），为它耗 Flash 寿命不值得。

代价：想保存就要么上位机自己存档、要么改 `bms_config.h`。**协议层不用动**。

### 6.6 SOH 学习结果 / 累计与循环 / 工况折算

#### `0x20` RD_SOH_BLOB / `0x21` WR_SOH_BLOB

120 B 参数块，**与 `bms_nvm` 落盘载荷逐字节同布局**（见 `README.md` §8.6）。
上行是 `rc + 120 = 121 B`，下行是裸 120 B。

> **ver 2 → ver 3 的长度变化**：载荷从 68 B 加到 120 B，但**前 68 字节一个字节都没动**
> —— 放电方向 R0 / 标定基线 / 样本数 / 容量 / 温度 / 卡尔曼协方差 / 三个标志全部原位，
> 新增的充电方向 R0 与累计充放电追加在 68 之后。
> 所以"只解前 68 字节"的老上位机代码**仍然能拿到完全正确的旧字段**，只是看不到新字段；
> 而收发长度必须按 120 B 来（这是 `proto_ver` 从 1 提到 2 的唯一原因）。
> 逐字节布局见 `bms_nvm.h` 表头；工具侧用 `bms_tune_proto.soh_blob_decode()` /
> `soh_blob_encode()`，`SOH_BLOB_BYTES_V2 = 68` 是旧视图的长度。

典型用途：把一台机器学到的 SOH 结果灌到另一台（同型号电芯换板子时免重新学习）。

> 这两个命令**依赖 `BMS_USE_NVM`**：它们直接复用 `BMS_NVM_ParamToBytes` / `BytesToParam`，
> 关闭持久化时返回 `rc = 3`。这样安排是为了**不写第二份序列化** ——
> 两处各写一份必然会有一次忘了同步，而参数错位在板子上极难定位。

#### `0x22` RD_SOH_SUM

只读摘要，上位机显示用。上行（15 B）：

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 1 | rc |
| 1 | 2 | SOH（0.01 %）u16 |
| 3 | 1 | SOH 整数 % |
| 4 | 1 | 容量保持率 % |
| 5 | 1 | 内阻指标 % |
| 6 | 4 | 学习容量 mAh u32 |
| 10 | 2 | R0 均值 mΩ u16 |
| 12 | 2 | 当前温度（0.1 °C）i16 |
| 14 | 1 | 有效标志：bit0 容量有效，bit1 内阻(放电)有效，bit2 内阻(充电)有效，bit3 计数有效 |

```python
soh01, sohp, cap_p, r_p = struct.unpack_from('<HBBB', pay, 1)
q, r0, t = struct.unpack_from('<IHH', pay, 6)

```

#### `0x23` SOH_RESET

清学习值，回到"没学过"状态。

> **库内部已经处理了正确顺序**：先把 R0 活跃值打回"当前温度的出厂基准"，再 `SOH_Init()`。
> 反过来的话 `SOH_Init()` 会把"含老化量的 R0"快照成分母，**SOH_R 从此恒等于 100%**。
> 这个坑和 `bms_nvm` 上电导入时"先切温度再导入"是同一类。你直接发命令就行，
> 但如果你在自己的代码里手工做这两步，务必按这个顺序。

#### `0x24` RD_SOH_CNT

累计充放电与循环次数。**五个数都是从"学到现在"的累计量**，不是瞬时值。上行（16 B）：

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 1 | rc |
| 1 | 4 | 累计充入电量 mAh u32 |
| 5 | 4 | 累计放出电量 mAh u32 |
| 9 | 2 | 半循环计数（摆幅法）u16 |
| 11 | 4 | 等效满循环 ×1000 u32 |
| 15 | 1 | 计数有效（1 = 至少累计过一次充放）|

```python
chg, dis, half, cyc_milli = struct.unpack_from('<IIHI', pay, 1)
valid = pay[15]
```

两个循环口径是**互补**的，别把哪个当唯一真值：

| 口径 | 定义 | 特点 |
|---|---|---|
| 半循环计数 | SOC 自本段极值回升/回落超过 `SOH_CYCLE_SWING_01`（默认 30%）记半个 | 与电池手册的"循环寿命"同口径，但受放电深度影响 |
| 等效满循环 | 累计放出电量 ÷ 标称容量 | 与放电深度无关，看老化趋势更干净 |

> 累计只在**真的在充放**时进行（`|I| > SOH_IDLE_MA`）。静置时的电流噪声（约 ±19 mA）
> 不进长期统计 —— 否则一台放着不用的机器也会"累计"出几十 Ah。
>
> 落盘不是每帧做：累计量每帧都在变，若每帧置脏会把掉电保持的 60 s 去抖一直续期，
> 退化成"每 60 s 一写"（每天 1440 次），十几天磨穿 2 槽介质。所以总吞吐量涨够
> `SOH_COUNT_SAVE_PCT`%（默认 100%，即约 33.5 Ah）才置脏写一次。

#### `0x25` SOH_CNT_RESET

只把累计充放电与循环计数清零，**学到的容量与 R0 一点不动**。换电芯后归零用。

> 别和 `SOH_RESET`（`0x23`）搞混：后者清的是学习值。换新电芯时两个都要发。
> 清完会立刻置脏，要马上持久化就再发一条 `NVM_SAVE`（`0x30`）。

#### `0x26` RD_R0_CHG_ALL / `0x27` WR_R0_CHG_ALL

**充电方向**那张 R0 表，格式与 `0x12` / `0x13` 完全一样（22 B = 11 点 × 2 B）。
放电方向仍是 `0x12` / `0x13`。

> 板子按充/放两个方向**各学一张表**：同一个 SOC 点上两个方向的表观内阻并不相等
> （充放电过电位不对称；而且是在 200 ms 尺度上量的，已含一部分快的电荷转移阻抗），
> 把两个方向混在一格里做指数平滑会让两边都不准。EKF 的量测方程按当前电流方向取用，
> `soh.c` 也按方向各自学习、各自计数（方向在进入带载段时按电流符号定一次，整段沿用）。
>
> `SOH_R`（内阻指标，就是容量保持率旁边那个）用的是**放电**方向；充电方向的指标只在
> `RD_SOH_SUM` 的 flags 里给一个"有没有学到"的标志位，绝对值不要与 `SOH_R` 直接比。

#### `0x28` RD_CORR

读当前工况的容量折算系数与折算后的可用容量（温度 / 倍率修正，配置见 `bms_config.h [10]`）。
上行（15 B）：

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 1 | rc |
| 1 | 4 | 折算系数 K（ppm，1e6 = 100%）i32 |
| 5 | 4 | 折算后可用容量 mAh u32 |
| 9 | 2 | 参考温度（0.1 °C）i16 |
| 11 | 4 | 参考电流 mA i32 |

```python
k_ppm, eff_mah, ref_t, ref_i = struct.unpack_from('<iIhi', pay, 1)
```

`K = f_T(T) × f_I(|I|)`，归一化到参考工况（默认 25 °C / 0.2C = 670 mA，即 `BMS_REF_TEMP_DC` / `BMS_REF_CUR_MA`）：

- `f_T` 由 `SOC_CAP_TEMP_PCT` 按温度线性插值 —— 低温下锂电可用容量会掉 20~30%；
- `f_I` 是 Peukert 修正 `(|I| / I_ref)^(1-k)` —— 大倍率同样让可用容量变小。

**未标定时 K 恒等于 100%**（`SOC_CAP_TEMP_PCT` 全 100 且 `SOC_PEUKERT_K = 1.0`），
此时算法里的折算路径与不折算**逐位相同** —— 所以看到 100% 是正常的，不是命令没生效。
标定后它会随温度与电流实时变化。

> 为什么需要它：容量学习（`SOH_Q`）是拿实测 `ΔQ / ΔSOC` 算出来的。低温或大倍率下
> 测出来的 Q 会偏小，若直接学进去，一次冬天或大电流的试验就被当成"电池老化了"
> 永久留在 SOH 里（而且卡尔曼对下跳几乎不设防）。所以 `soh.c` 在融合前先按区间平均
> 温度与平均电流把 Q 折回参考工况：`Q_ref = Q_meas / (f_T × f_I)`。
>
> 折算做在**电流**上而不是每帧可用容量上：
> `SOC_AhUpdate` 的累加器按 `I·Δt·65536/K` 累积，分母恒定，K = 1 时与不折算逐位等价。
> 若改成"每帧用当前可用容量换算电量"，整数除法会把不足 1 LSB 的部分截掉
> （2000 mA × 200 ms ÷ (360 × 3350) = 0.33 LSB，每帧都截成 0），积分会完全失效。

### 错误 4：整组里有一个值越界

WR_EKF 的 `q_soc` / `r_v` 都合法，但 `p_min` 写了 1e30（上界 1e4）。**两趟校验，整组不写**
—— 执行完再读回来，8 个参数和写之前逐字节相同。

```
下行  AA 55 20 00 19 6F 12 03 3B 00 00 00 3F 00 00 A0 41 00 00 20 41 00 00 C8 43 00 00 7A 43 BD 37 86 35 CA F2 49 71 33 1D
上行  AA 55 01 00 99 01 26 40    → rc = 1
```

### 错误 5：CRC 校验失败

```
下行  AA 55 05 00 03 00 00 0A E1 10 13 BE   （正确的最后一字节是 41）
上行  （无应答，0 字节）
错误计数  0 → 1
```

### 帧同步自恢复

- 垃圾前缀 `00 13 FF 7E` + 完整帧 → rc = 0，写入值 = 4321 ✓
- 重复前导 `AA AA` + 完整帧 → rc = 0，写入值 = 4321 ✓

## 8. 上位机实现指南

### 8.1 启动流程

```
1. PING                   确认在线 + proto_ver 对得上
2. INFO                   拿 temp_n / tbl_n / soc_n / cal_bytes，后面的解包全靠它
3. RD_CAL_TEMPS           知道三个温度点分别对应哪个 ti
4. RD_TEMP                知道当前温度（决定你改哪个 ti 会立刻生效）
```

要动 SOC / EKF 时再加两条：`RD_SOC` 看估计器当前状态（`base01` / `coul` / `P11` 能判断它有没有收敛），
`RD_EKF` 拿到正在跑的 8 个参数 —— **写之前先读**，一是没有单参数写、必须整组回写，
二是改完要有个基准能对比。

**别硬编码 264。** 改了 `bms_config.h` 里的温度点个数，`cal_bytes` 会变，
硬编码的上位机会静默错位 —— 这是最难查的那类 bug。

### 8.2 超时与重试

| 情况 | 表现 | 怎么处理 |
|---|---|---|
| CRC 错 | **无应答** | 只能靠超时重传 |
| 超长帧 | **无应答** | 检查 `BMS_TUNE_RX_MAX` |
| `rc = 1` / `rc = 2` | 有应答 | **你的 bug，别重试**（重试 N 次还是同一个错） |
| `rc = 3` | 有应答 | 功能没编译进库，换命令或改开关 |

应答是在 `BMS_TUNE_Feed()` **内部同步发出**的 —— 收到最后一个 CRC 字节就执行并回吐。
所以超时可以设得很短（串口 115200 下几十 ms 足够）。

### 8.3 改标定表的正确姿势

```
RD_CAL_ALL  →  在内存里改你要改的点  →  WR_CAL_ALL 整包写回
```

**不要自己从零拼一套新表** —— 你只有 25 °C 的数据时，把 5 °C 和 45 °C 写成 0 会让
低温插值彻底崩掉。读改写才不会漏掉没标定的温度点。

单点命令 `0x03` 是给你微调用的，批量改一定走整包。

### 8.4 其它要点

- **批量优先**：改 R0 用 `WR_R0_ALL`（1 帧 22 B）而不是 11 次 `WR_R0`（11 帧）
- **写完读回确认**：尤其容量（会被静默钳位）
- **标定表掉电丢失**：上电后你的程序要重新下发（见 §6.2）
- **改完想保存**：`NVM_SAVE`（只保存 SOH 参数，标定表不落盘）

## 9. 下位机接线指南

> 本节是**最小骨架**。完整的移植步骤、三个平台的参考实现、症状对照表、
> 与上位机对齐的五步验收，见 **`移植与对齐指南.md`**。

### 9.1 三步

```c
static ring_t g_rx;                              /* 你自己的接收环形缓冲 */

void UARTx_IRQHandler(void)                      /* 中断里只塞字节 */
{
    if (RXNE) ring_put(&g_rx, USART_ReceiveData());
}

int main(void)
{
    BMS_TUNE_SetTx(uart_putc);                   /* 1. 注册"发一个字节" */
    for (;;)
    {
        while (ring_avail(&g_rx))
            BMS_TUNE_Feed(ring_get(&g_rx));      /* 2. 主循环里解析 + 执行 */
        /* ... */
    }
}
```

3. `bms_config.h` 的 `[9]` 组把 `BMS_USE_TUNE` 改成 `1`。

### 9.2 三条硬边界

1. **中断里绝不能调 `BMS_TUNE_Feed()`。** 主循环的 `SOC_AhUpdate()` 正在读标定表，
   中断里改表会读到"一半新一半旧"。中断只负责往环形缓冲塞字节。
2. **`BMS_NVM_Save()` 也不能进中断**（擦页要关中断 10~20 ms）。
   `BMS_TUNE_Feed()` 会调它，所以这条是上一条的推论。
3. **`tx` 回调里别做太重的事。** 它在 `Feed()` 上下文里同步调用，
   不要 `while` 等发送完成标志等几百 ms。通常是"查询发送寄存器空 → 写入"或塞进发送环形缓冲。

### 9.3 开销

| 项 | 值 |
|---|---|
| Flash | **+3022 B**（`BMS_USE_TUNE=1` 实测；设为 0 时目标文件 **0 字节**） |
| RAM | **+291 B**（接收缓冲 `264+8+3 = 275 B`，应答复用同一块，否则要再加 264 B） |
| 单字节 | 非 payload 阶段一次 switch；CRC 整帧只算一次 |

不需要在线调参就把开关关掉，一个字节都不占。

### 9.4 鉴权

**库不做任何鉴权**（见 §10）。要不要开放、什么时候开放由工程侧决定，三种典型做法：

- 上电后 N 秒内允许调参，超时后不再把串口数据喂给 `Feed()`
- 检测到某个握手序列（比如连续收到特定字节）才允许
- 物理按键按下时才接通

实现上就是**控制"要不要调 `BMS_TUNE_Feed()`"这一行**，不需要改库。

<a id="10"></a>
## 10. 安全须知

**本模块不做任何鉴权。** 谁能往 `BMS_TUNE_Feed()` 里喂字节，谁就能改标定表、改容量、
清 SOH 学习结果。

**改错了不会让固件崩溃**（所有越界都被挡住，索引检查是完整的），**但会让 SOC 算错** ——
后者更危险，因为它不报错，只是慢慢偏。

具体风险：

| 操作 | 后果 |
|---|---|
| 改 OCV 表 | SOC 直接偏，且 OCV 重同步时会把错误的 SOC 当成真值 |
| 改容量 | 库内钳到 50%~110%×标称，但区间内写错照样让 SOC 比例全错 |
| 清 SOH（`0x23`） | 学到的容量和内阻归零，要重新学几个小时 |
| 改 R0 活跃值 | 影响内阻补偿和 SOH_R |
| 强制设 SOC（`0x17`） | 把估计值对齐到你填的数。填错了比不填更糟：它会一路带着这个错值算下去，直到下次静置重同步 |
| 改 EKF 参数（`0x19`） | `q_soc` 调太大会让 SOC 跟着端压噪声乱跳，`r_v` 调太大则滤波器钝化、长时间不纠偏。这两项在板子上表现为"数看着挺稳/挺活跃"，出了问题不容易联想到是参数 |
| 复位 EKF（`0x1A`） | 协方差回到 P0 初值，滤波器重新收敛，期间 SOC 会有一段跟随过程。不丢学习结果 |

EKF 参数的**合法性**固件只能挡量级（非正 / NaN / 离谱量级），**好坏它判不了**。
试参数的正规做法是先在 PC 上用 `脚本/test/kalman_tune.py` 回放采集数据（§9 的
`stair` 静置末参考点），选出来再写板子。

**量产固件建议默认关闭 `BMS_USE_TUNE`**，只在标定工装/开发版本打开。

<a id="11"></a>
## 11. 版本与兼容

### 11.1 版本号

| 版本 | 载体 | 语义 |
|---|---|---|
| `proto_ver` | `BMS_TUNE_PROTO_VER`，`PING` / `INFO` 可读 | **帧格式或命令语义**变了就 +1 |
| `nvm_ver` | `BMS_NVM_VER`，`INFO` 可读 | 落盘载荷布局变了就 +1 |

当前：`proto_ver = 2`，`nvm_ver = 3`。

> **2 / 3 是怎么来的**：新加了"充电方向 R0"与"累计充放电"两块持久化字段，
> 落盘载荷 68 → 120 B，所以 `nvm_ver` 2 → 3。
> 同时 `RD_SOH_BLOB` / `WR_SOH_BLOB` 的载荷长度跟着从 68 变成 120，
> 属于"改现有命令的 payload 布局"，所以 `proto_ver` 也必须 1 → 2。
> 前 68 字节的布局保持不变 —— 只解旧字段的老代码仍能正确工作。

上位机启动时应比较 `proto_ver`，不一致就提示升级，**不要硬着头皮继续对话**。

### 11.2 命令空间

命令字最高位被应答标志占用，所以可用范围是 `0x00 ~ 0x7F`，按高 4 位分组：

| 段 | 用途 |
|---|---|
| `0x0_` | 链路自检 + 标定表 |
| `0x1_` | R0 活跃值 + 容量 + **SOC 运行态与 EKF 参数**（`0x16`~`0x1A`） |
| `0x2_` | SOH + 充电方向 R0（`0x26`/`0x27`）+ 工况折算（`0x28`）|
| `0x3_` | 掉电保持 |
| `0x4_` | 实时量 |
| `0x5_` ~ `0x7_` | 保留给将来 |

段内未使用的命令字返回 `rc = 3`（`ENOSUP`）。上位机收到 `rc = 3`
应判为"固件版本比上位机老"，而不是通信故障。

### 11.3 兼容性承诺

- **加命令不改 `proto_ver`**（新命令对老上位机透明，老上位机不用它就不会发；
  `0x24`/`0x25`/`0x26`/`0x27`/`0x28` 就是这么加的）
- **改现有命令的 payload 布局必须 +1**（`proto_ver` 之所以是 2，就是因为
  `0x20`/`0x21` 的载荷从 68 变成了 120 B）
- **改 CRC 参数或覆盖范围必须 +1**

## 12. 排错清单

| 现象 | 最可能的原因 |
|---|---|
| 发下去完全没反应 | ① `BMS_USE_TUNE` 没改成 1 ② 在中断里调了 `Feed()` ③ 主循环没跑到这里 |
| 能发能收但一直无应答 | `BMS_TUNE_SetTx()` 没注册（库会直接丢弃应答） |
| 一直 `rc = 2` | payload 长度不对 —— 对照 §6 每条命令的长度表 |
| 一直 `rc = 3` | 功能没编译进库（`BMS_USE_NVM=0` 时的 `0x20/0x21/0x30/0x31`），或命令字拼错 |
| 一直 `rc = 1` | 索引越界 —— `ti` 0~2、`tbl` 0~3、`idx` 0~10 |
| CRC 总对不上 | **CRC 覆盖范围错了**：是 `LEN+CMD+PAYLOAD`，**不含 `AA 55`** |
| 改了标定表没效果 | 当前温度不是你改的那个温度点。用 `RD_TEMP` 确认，或 `WR_TEMP` 切过去再看 |
| 改 5 °C 的表，25 °C 的活跃表没变 | **这是对的**，温度解耦。用 `RD_CAL_ACTIVE` 看当前温度的活跃表 |
| 写容量写进去的数不是我发的 | 被钳到 `[50%, 110%] × 标称`。写完 `RD_CAP` 读回确认 |
| 写 EKF 参数回 `rc = 1` | 8 个值里有出界的。每个参数的合法区间见 §6.5 的表（**开区间**：恰好等于上下界也判越界） |
| 写 EKF 参数回 `rc = 2` | 下行必须是 **32 字节**（8 × f32）。少一个参数、或多给一个都会是 2 |
| 改完 `p0_soc` / `p0_vrc` 没反应 | 这两个只在 EKF 建立 / 复位那一次用 —— 补发一次 `EKF_RESET` |
| 强制设 SOC 之后又跳回去了 | 静置满 `SOC_IDLE_MS` 后重同步把 SOC 拉向 OCV 表读数。**这是设计**，不是命令失效；设过之后走半衰限幅，所以只会慢慢回 |
| `RD_SOC` 的 `P11` 一直是 0 | `flags` 的 bit0 大概是 0 —— EKF 还没建立（`SOC_AhUpdate()` 一次都没跑过）。用 `WR_SOC`、或让主循环正常跑起来 |
| 大包（264 B）发不出去 | 帧超过 `BMS_TUNE_RX_MAX`（默认 272）会被直接丢弃，不计数应答 |
| 偶尔丢一帧 | 正常。串行线路有干扰时用超时重传兜住；库不提供重传机制 |
